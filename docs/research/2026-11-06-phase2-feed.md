# Phase 2: what one `bw feed` read costs

Run on macmini (Apple M4 Pro), 2026-11-07, with the release build of `bw`
0.2.0, by `scripts/verify/feed-cost.sh` (5 runs per case). Each case reads
a scratch copy of the largest Claude log and the largest Codex rollout on
this Mac with `bw feed --log <copy> --agent <k> --pictures`. The table holds
the child's user plus system time from `getrusage`, in milliseconds.
`/usr/bin/time -l` rounds to 10 ms and printed 0.00 for every case, so the
script reads the child's resource usage instead.

| Log | Size | Read | Median ms | Max ms | Answer |
| --- | ---: | --- | ---: | ---: | --- |
| Claude | 143,051,105 B | first read | 8.8 | 13.9 | 131 rows |
| Claude | 143,051,105 B | unchanged cursor | 2.6 | 2.7 | `unchanged` |
| Claude | 143,052,330 B | one appended line | 9.0 | 9.1 | `splice` at 131 |
| Codex | 39,515,694 B | first read | 6.1 | 6.7 | 16 rows |
| Codex | 39,515,694 B | unchanged cursor | 2.5 | 2.6 | `unchanged` |
| Codex | 39,516,560 B | one appended line | 6.6 | 6.7 | `splice` at 16 |

## What the numbers say

- A read costs at most 14 ms of CPU, under the spec's 100 ms rule, because
  `bw` parses only the last 2 MB of a log (`tail::BYTES`), however large
  the file is.
- An unchanged cursor costs about 2.5 ms: `bw` compares the size and the
  cursor and parses nothing.
- An appended line parses the kept range again (up to 8 MB,
  `feed::MAX_SPAN`) and sends only the rows from the first one that
  changed. The appended line repeated the log's last record, which adds no
  row, so both splices start after the last row.
- A shown chat polls every 2 s, so one chat's reads cost about 0.1 % to
  0.5 % of one core. Phase 7 decides on a watcher with these numbers.
- Running the cursor cases more than once against one saved cursor needs
  the cache restored before each run. Without it, every run after the
  first sees a cursor the cache no longer matches and answers `splice` at
  0, the full window. The script copies the cache back before each run.
